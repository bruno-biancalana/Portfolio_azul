A/B testing in SPAs: JavaScript, Adobe Target and performance

By Bruno Biancalana · 14/10/2026 · Technical article

Single-page applications can change views without reloading the document. For A/B testing and personalization, that creates a practical challenge: an experience must appear at the right time, only where it belongs, without harming the page.

Why SPAs change the experimentation lifecycle

In a traditional page load, an experiment often runs after a document is ready. In an SPA, client-side navigation can replace components, update routes, or render elements asynchronously. A selector that exists now may disappear on the next view, while a new target may not exist yet.

This matters when using tools such as Adobe Target: audience and experience configuration are only part of the work. The front-end implementation also needs to respect the application's rendering lifecycle.

Five engineering practices

  1. Define an explicit activation condition. Check the intended route, audience context and target element before applying a change.
  2. Keep execution idempotent. Re-running an experiment should not duplicate banners, event listeners or visual changes.
  3. Observe only when necessary. A scoped MutationObserver can help detect asynchronously rendered content, but disconnect it once the target is found or the experiment is no longer relevant.
  4. Plan for route transitions. Decide what should happen when the user navigates to another view without a full reload, including cleanup of temporary changes.
  5. Measure without duplicating events. Separate exposure, interaction and conversion events, and verify that each is fired under the intended conditions.

A simplified, framework-independent example

The following is an illustrative pattern, not code from an employer or a production implementation. It waits for a target element and applies a change only once. A real implementation should also handle route changes, cleanup and experiment eligibility.

Illustrative example · JavaScriptNot production-ready
function applyOnce(element) {
  if (element.dataset.experimentApplied === 'true') return;
  element.dataset.experimentApplied = 'true';
  element.classList.add('experiment-variant');
}
function waitForTarget(selector, timeoutMs = 5000) {
  const existing = document.querySelector(selector);
  if (existing) { applyOnce(existing); return; }

  const observer = new MutationObserver(() => {
    const element = document.querySelector(selector);
    if (!element) return;
    applyOnce(element);
    observer.disconnect();
    clearTimeout(timeout);
  });
  observer.observe(document.body, { childList: true, subtree: true });
  const timeout = setTimeout(() => observer.disconnect(), timeoutMs);
}
waitForTarget('[data-experiment-target]');

Performance, accessibility and measurement

Even a correctly displayed variant can be a poor experiment if it causes layout shifts, blocks interactions or creates inconsistent analytics. Validate behavior on mobile and desktop, account for keyboard interactions, and monitor relevant performance indicators alongside conversion metrics.

For measurement, define what constitutes an exposure before implementation. Use a consistent event naming scheme and check analytics tools such as GA4/GTM for accidental double counting, especially during SPA navigation.

The engineering takeaway

Reliable experimentation is not just a matter of changing text or colors. It requires understanding application state, asynchronous rendering, lifecycle management, observability and user experience. These principles apply across experimentation platforms, including Adobe Target.
